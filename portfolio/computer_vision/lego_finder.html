Overview

Lego Finder is a vision-based real-time LEGO brick matching model. The project targets a familiar problem: when many LEGO parts are scattered on the floor or desk, finding one required brick can interrupt the building flow. The proposed system lets a user point a smartphone camera at a mixed pile and receive visual guidance toward the requested part.

The model is designed as an application of my previous ROI masking and HNSW-based image matching research. Instead of searching every feature in a full frame, the system first predicts the region where the target part is likely to exist, extracts compact visual features only from that area, and queries an offline LEGO part index for fast matching.

Difference From Existing Apps

Existing LEGO-related AI apps often focus on adjacent use cases. Brickit scans bricks and suggests things to build, while inventory-oriented tools such as Pileometer assume a more controlled setup for labeling and managing stored parts. Lego Finder focuses on the assembly-time search problem: the user already knows the part they need and wants to find it quickly in a cluttered pile.

Pipeline

1Encode Query

Convert text, voice, or instruction-image input into a fixed prompt embedding with a vision-language encoder such as CLIP.

2Match LEGO DB

Map the query to Rebrickable-style part metadata, official color records, and rendered part references.

3Predict ROI

Use a MobileNet-style visual backbone and cross-modal attention to produce a prompt-guided ROI probability map.

4Search Features

Binarize and dilate the ROI, extract ORB-like features only inside the mask, then query an offline HNSW index.

5Verify & Visualize

Use RANSAC to reject inconsistent matches, estimate the target pose, and render an AR-style brick highlight.

01

Learning Signal

Triplet-based ROI supervision

The ROI model is trained with an input image, target prompt, and ground-truth mask. Copy-paste augmentation places rendered LEGO parts on real backgrounds when manually labeled masks are limited.

02

Loss Design

BCE plus Dice loss

Binary Cross Entropy scores each spatial cell, while Dice Loss improves mask overlap. The goal is to raise confidence only around the requested brick and suppress visually similar distractors.

03

Runtime Strategy

Offline index, online query

HNSW is not rebuilt during live camera use. LEGO part descriptors are indexed offline before service time, so the runtime only sends compact frame descriptors as queries and verifies the returned candidates geometrically.

Challenges & Solutions

1 Occluded or Partially Hidden Blocks
Challenge

Real piles often hide part of a brick behind other pieces, making feature matching less stable.

Solution

Fuse auxiliary cues such as color distribution, partial shape evidence, and verifier confidence so the target can still be recovered from incomplete visual evidence.

2 Domain Gap Between Manual Images and Real Photos
Challenge

Instruction images, official rendered parts, and real camera photos differ in lighting, shadows, and texture detail.

Solution

Use lightweight preprocessing, including HSL color-space normalization, to reduce lighting interference before feature extraction and matching.

3 Color Confusion and Non-LEGO Distractors
Challenge

A same-colored non-LEGO object, or a mixed-color part with a small patch of the target color, can be ranked too highly if color is over-weighted.

Solution

Adjust scoring around dominant object color, rectangularity, polygon corner count, and geometric verification so the model distinguishes target bricks from incidental color matches.

4 Merged ROI Components
Challenge

Multiple nearby blocks can merge into one large connected component, causing the ROI to cover too much of the frame.

Solution

Refine proposals by splitting target-color connected components and adding boundary evidence such as Sobel gradient cues before final verification.

Reflection & Future Work

  • Reflection: This was my first project using Codex as a practical development partner to move beyond model design and build a fuller prototype. It was especially helpful for backend API structure, server execution, and hosting-related workflows that I had not studied deeply before. At the same time, the process showed me that AI-assisted development still requires active review, testing, and judgment because generated code can contain assumptions that do not match the actual project goal. Working across the frontend, backend, image-processing logic, and API flow also helped me understand the overall structure of a full-stack AI application, where usability, data handling, runtime efficiency, and validation matter as much as the model itself. However, the prototype still had clear constraints. To keep the project scope manageable, I limited the target parts to basic rectangular m-by-n bricks, and I would like to expand this work into a more complete service that can handle a broader range of LEGO parts.
  • Future Work: Improve occlusion robustness, reduce render-to-photo domain gap, fine-tune color and shape scoring, cache frequently used basic bricks, and evaluate latency on real mobile hardware.
