Game Development

Stand-By

Mar 2024 - Jun 2024 Technical Lead 2nd Place GAM150 Project ˙ 2025 Micro Degree Expo
C++ Raylib Custom Engine

Overview

Stand-By is a cafe management game created by Team Half & Half. The player runs a cafe as both the manager and the only employee, serving customers while trying to earn enough money to pay late rent. The core interaction loop centers on making drinks under pressure. Players pour sodas, prepare blends with ingredients, shake the shaker, chill the cup, and deliver completed drinks to customers before the cafe closes.

Key Achievements

  • Placed 2nd(Outstanding Award) at the 2025 Micro Degree Expo.
  • Implemented core gameplay states and contributed to the development of key engine systems.
  • Conducted iterative playtesting and self-QA to identify, reproduce, and resolve gameplay bugs, improving overall stability.
  • Connected player interactions to clear visual feedback and responsive timing cues.

My Role

My role was to keep the cafe simulation readable as code. I tracked and managed state such as what the player was pointing at, what tool or drink was currently selected, which drink-making step was active, whether the current order could be served, and how much time remained in the day.

  • Led the overall code structure for the main cafe loop as the team's technical lead.
  • Implemented gameplay algorithms while shaping the engine pipeline so new features could remain stable as the project scope grew.
  • Defined game states clearly, managed transitions between them, and separated object-interaction logic so the game could behave predictably.
  • Tracked interaction bugs and edge cases during playtesting, especially issues that appeared only after repeated day-to-day runs.

Technical Highlights

Game Object Interaction

Used C++ pointers to route interactions between active game objects, then applied outline feedback to the selected object so the player could immediately read what the cursor was targeting.

Game Engine Architecture

Extended a lightweight engine layer around raylib with project-specific state, object, collision, and scene-management helpers to keep gameplay code reusable and easier to maintain.

Progression Balancing

Tuned day-based difficulty through recipe availability, customer spawning, requested drink variety, and penalties for failed service so later days felt busier without changing the core controls.

Challenges & Solutions

1 Customer System Complexity
Challenge

At one point, every customer was being managed through the same class-level behavior, so they tended to appear together and disappear together instead of behaving like independent visitors.

Solution

We gave each customer object its own spawn and waiting timers, allowing individual customers to appear, wait, and leave after their own time window instead of sharing one synchronized lifecycle.

2 Object Collision/Interaction
Challenge

The player needed clear feedback about which object was selected, and we also had to keep interaction rules separated across many objects instead of letting one large collision block handle everything.

Solution

We added outline feedback for selected objects and split interaction handling by context: selection, ingredient insertion, shaker movement, cup chilling, inventory delivery, and customer serving each had its own rule path.

3 Game Level Design
Challenge

As the game expanded across multiple in-game days, we had to think carefully about recipe accuracy, penalties for failing to serve the requested drink, customer frequency, and how drink difficulty should increase by day.

Solution

We tied progression to day count: available recipes expanded gradually, customer behavior became more demanding, and the daily script state gave the player a clean break before the next round of cafe pressure.

Reflection

Stand-By showed me how quickly a management game can become a systems problem. A single customer order affects the UI, input handling, collision logic, recipes, inventory, timers, currency, and scene transitions, so the experience only feels reliable when all of these systems remain synchronized.

The project also made me more aware of memory management. Because the game progresses through repeated daily cycles, small mistakes in resource ownership or cleanup can accumulate into memory leaks during long play sessions. If I were rebuilding the system, I would define clearer ownership rules, verify cleanup during repeated state transitions, and test long-running sessions much earlier in development.

One limitation was that the development schedule left little time for optimization and structural refactoring. Several objects with similar behavior were implemented as separate classes, which increased duplication and made the codebase longer and harder to maintain. This experience taught me to identify shared behavior earlier and use inheritance where appropriate to build reusable abstractions in future projects.
